Two taps, one pickup

Two volunteers in Baltimore tap Claim on the same tray of bagels in the same instant. What happens next is the whole argument for building this on SpacetimeDB instead of a REST API.

The same moment, two architectures

Time runs downward. Both volunteers act inside the same 40 milliseconds.

Express + Postgres REST
  1. +0ms Ella — GET /listings/30 Reads claimed_by: null
  2. +12ms Vanessa — GET /listings/30 Also reads claimed_by: null. Ella has not written yet.
  3. +18ms Ella — POST /claim Server checks its copy: still null. Writes Ella.
  4. +24ms Vanessa — POST /claim Server checked before Ella's write landed. Overwrites with Vanessa.
  5. +2s Both screens still read “yours” Neither client polls again until its interval elapses.

✕ Two drivers dispatched. One tray of bagels.

Module inside the database SpacetimeDB
  1. +0ms Ella — calls claim_listing(30) Queued as a transaction.
  2. +12ms Vanessa — calls claim_listing(30) Queued behind it. Reducers do not interleave.
  3. +18ms Transaction 1 runs to completion Sees None, writes Ella, commits.
  4. +19ms Transaction 2 runs next Sees Some(Ella) — cannot see the state T1 saw. Returns Err, writes nothing.
  5. +21ms Both screens update, unprompted Vanessa’s reads “Ella claimed this first.”

✓ One driver. The loser is told why.

The REST version is fixable — that's the point

SELECT … FOR UPDATE, an optimistic version column, or a compare-and-swap retry loop all close that gap. Each is code you write, test, and get right. We wrote none of it. Serialized transactions are what a reducer already is, so the correct behaviour is the default rather than the thing you remembered to add.

Three numbers we can defend

No synthetic benchmark. Each of these is either arithmetic or something a judge can verify on the machine in front of them.

Staleness 2.5s → 0

A 2-second poll leaves an average one-second window, and a 5-second poll leaves 2.5, where two drivers both see “open”. Push closes it to network latency. This gap is the double-dispatch bug.

Data layer 2

Two useTable calls are the client's entire data layer. No fetch, no polling, no cache, no store — the repo contains zero data-fetching code.

Backend ~190

Lines of Rust: two tables, five reducers, input validation. That is the whole server. There is no API layer because the reducers are the API.

What we didn't have to build

The honest comparison isn't speed. It's the list of things that never became our problem.

REST routes for listings, claims, releases, completions not written
A websocket server, plus fan-out to connected clients not written
Client-side cache and invalidation on every mutation not written
Row locking or compare-and-swap for the contested claim not written
An auth layer to stop a client claiming to be someone else not written
What we did write 2 tables · 5 reducers · 2 subscriptions

Identity is the clearest case. claim_listing takes one argument, the listing id. There is no parameter for who — it comes from ctx.sender(), established by the connection. A client cannot forge it, because there is nowhere to put it.

The receipt

Two claims on listing 30, launched from one shell line so both are in flight before either returns. 

$ spacetime call -- food-pickup claim_listing 30 & \
  spacetime call -- food-pickup claim_listing 30 & wait
[1] 60949
[2] 60950

[1]  - done       spacetime call -- food-pickup claim_listing 30
Error: Response text: Ella CLI claimed this first.
[2]  + exit 1     spacetime call -- food-pickup claim_listing 30

$ spacetime sql food-pickup "SELECT id, claimed_by FROM listing WHERE id = 30"
 id | claimed_by
----+------------------------------------------------------------
 30 | (some = (__identity__ = 0xc200af83…))

Both PIDs are assigned before either process exits. One exits 0, the other exits 1, and the row afterwards has exactly one holder.
